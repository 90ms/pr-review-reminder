# 실행 계획 — PR Review Reminder

> 현재 구현을 안전한 공개 배포 수준으로 끌어올리는 전향적 계획이다.
> 각 단계는 독립적으로 검토·되돌릴 수 있는 작은 커밋으로 진행한다.

기준 계약은 [`docs/SPEC.md`](../docs/SPEC.md)다. 모든 게시 기능은 사용자 액션
경계를 유지하고, 테스트에서는 실제 GitHub/AI 명령을 실행하지 않는다.

## 우선순위

| 단계 | 목표 | 주요 산출물 | 완료 조건 |
|---|---|---|---|
| 1 | 리뷰 정확성 | 현재 리뷰 요청 의미 반영, 게시 전 head SHA 재검증 | 새 커밋이 생긴 오래된 분석으로 무경고 승인하지 않음 |
| 2 | 로컬 데이터 보호 | 저장 고지, 저장 선택, 보존/삭제 정책, 파일 권한과 오류 처리 | 비공개 코드 저장 범위를 사용자가 이해하고 제어 가능 |
| 3 | 실행 제어 | CLI 타임아웃, 취소, 안전한 조회 재시도 | 멈춘 AI 작업을 종료하고 UI 상태가 복구됨 |
| 4 | 오케스트레이션 검증 | 주입형 러너 기반 `AppState` refresh/review 테스트 | 성공·실패·캐시 복원·취소 흐름 회귀 테스트 |
| 5 | 게시 원자성 | 단일 review 게시 또는 부분 성공 추적, 실패분 재시도 | 중복 코멘트와 부분 게시 후 잘못된 승인 방지 |
| 6 | 히스토리·비용 | 히스토리 상세/diff 열기, 재리뷰, Codex 단가 설정과 로컬 예산 | 과거 맥락 재사용 및 예산 제한을 설명 가능하게 제공 |
| 7 | UI 완성도 | 긴 diff 가로 스크롤, 창 제목 즉시 현지화, 앱 아이콘, 접근성 | 키보드·VoiceOver·다국어 수동 점검 통과 |
| 8 | 규모와 동시성 | 검색 페이지 처리, 조회 최적화, Swift 6 strict concurrency | strict concurrency 빌드와 대규모 목록 테스트 통과 |
| 9 | 공개 배포 | 라이선스, CI, 커뮤니티 문서, 릴리스·서명 정책 | 새 PR에서 자동 빌드/테스트, 설치 경로 문서화 |
| 10 | 최종 문서화 | README, 명세, 변경 로그, 소개 자료 동기화 | 구현·테스트·배포 방식과 문서가 일치 |

## 단계별 작업

### 1. 정확성 기준선

- GitHub가 현재 요청한 리뷰를 과거 리뷰 하나만으로 숨기지 않는다.
- 게시 직전에 현재 head SHA와 분석 SHA를 비교한다.
- SHA가 달라지면 게시를 중단하고 재리뷰 또는 명시적 계속 선택을 제공한다.
- 승인 경로와 코멘트 경로 모두 같은 검증을 사용한다.
- 회귀 테스트: 재요청, dismissed review, 새 commit, SHA 일치/불일치.

### 2. 히스토리 데이터 정책

- 최초 실행과 설정 화면에 저장 내용·위치를 알린다.
- 히스토리 저장 끄기, 보존 기간, 전체 삭제를 제공한다.
- diff 저장 여부를 별도 선택지로 검토한다.
- 파일은 사용자 전용 권한으로 만들고 읽기/쓰기/디코딩 실패를 노출한다.
- 마이그레이션과 삭제 동작을 테스트한다.

### 3. CLI 수명주기와 AppState

- 러너가 제공하는 timeout·task 취소를 GitHub/AI 작업별 정책에 연결한다.
- 자식 프로세스 종료와 stdout/stderr 회수를 계속 회귀 테스트한다.
- 진행 중 리뷰 취소, 창 닫기, 새로고침 시 상태 전이를 정의한다.
- 읽기 요청만 제한적으로 exponential backoff하고 쓰기는 자동 재시도하지 않는다.
- `AppState` 의존성을 주입 가능하게 정리하고 아래 흐름을 테스트한다.
  - 진단 실패 / 수집 성공·실패
  - 히스토리 cache hit / miss
  - 분석 성공·파싱 폴백·CLI 실패·timeout·취소
  - 스케줄 중복 실행 방지

### 4. 게시 안정성

- 가능하면 인라인 코멘트를 GitHub의 한 review 요청으로 묶는다.
- 불가능하면 각 코멘트의 성공 상태를 보존하고 실패분만 재시도한다.
- 게시 중 중복 클릭과 창 닫기를 막고 진행 상태를 표시한다.
- 모든 코멘트 성공과 SHA 일치를 확인한 뒤에만 승인한다.

### 5. 제품 기능 다듬기

- 히스토리에서 저장된 상세와 diff를 열고 최신 head를 재리뷰한다.
- 모델별 입력/출력 단가를 설정하고 추정치임을 표시한다.
- 히스토리 기간별 사용량으로 로컬 예산 한도를 근사한다.
- Split diff의 긴 줄을 가로 스크롤로 탐색한다.
- 언어 변경 즉시 메뉴/창 제목을 갱신한다.
- 앱 아이콘, 빈 상태 구분, 마지막/다음 새로고침 시각, 접근성 레이블을 추가한다.

### 6. 규모·마이그레이션

- 100개 검색 제한을 페이지 처리하거나 제한을 UI에 명확히 표시한다.
- PR별 순차 조회를 줄이고 안전한 동시성 상한을 둔다.
- diff 조회 실패와 입력 truncate를 화면에 노출한다.
- `SystemProcessRunner`, 저장소, `@MainActor` 경계를 Swift 6 strict concurrency로 이전한다.

### 7. 공개 저장소와 배포

- MIT `LICENSE`, `CONTRIBUTING.md`, `SECURITY.md`, 행동 강령을 추가한다.
- bug/feature 이슈 폼과 PR 템플릿을 제공한다.
- GitHub Actions에서 `swift build`, `swift test`, release build/앱 조립을 검증한다.
- 버전 소스, GitHub Release, Developer ID 서명·공증, 선택적 Homebrew Cask 정책을 정한다.
- 스크린샷/GIF는 실제 앱을 캡처한 뒤 README에 추가하고 출처 파일을 보관한다.

## 커밋 원칙

1. 기능, 테스트, 해당 문서 변경을 하나의 검토 가능한 커밋으로 묶는다.
2. 공개 저장소 위생, 동작 변경, UI 변경, 대규모 동시성 이전은 서로 분리한다.
3. 각 커밋 전 `git diff --check`, 관련 테스트, 가능한 경우 전체 `swift test`를 수행한다.
4. 실제 GitHub 코멘트·승인·이슈 생성은 검증 과정에서 실행하지 않는다.
5. 다른 작업자의 변경을 덮어쓰거나 커밋에 섞지 않는다.

## 공통 검증

```bash
swift build
swift test
./Scripts/build-app.sh
```

CI 환경에서는 앱 조립 결과의 `Info.plist`, 실행 파일, 번들 식별자와 버전을
검사한다. macOS 수동 검증에서는 CLI 진단, 메뉴바 배지, 상세 diff, 알림,
취소/timeout, 게시 미리보기까지 확인하되 실제 게시는 별도 명시적 스모크 절차로 제한한다.
